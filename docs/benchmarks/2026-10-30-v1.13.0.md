# Benchmarks — 2026-10-30 (v1.13.0, cyrius 6.7.18)

The 1.13.0 minor against 1.12.3. Both columns are DCE builds at the same toolchain (cyrius 6.7.18, cmdit 1.5.0). The previous snapshot is [`2026-10-30-v1.12.3.md`](2026-10-30-v1.12.3.md); the 1.12.x closeout baseline is [`2026-10-20-v1.12.2.md`](2026-10-20-v1.12.2.md). The CSV beside this file is the new baseline.

The host ran at a load average of 7–17 on 16 cores throughout, never quiet. Every comparison below alternates the two builds under the same conditions, and the load is given with each table.

## Commands

CPU time of each child, minimum of 9 runs, the two builds alternating in order and then in reverse (load 7–10). The fixtures were written by 1.12.3; 1.13.0 reads them unchanged. On tmpfs, so a sync costs nothing here: the on-disk effect of 1.13.0's add is in the next table.

| operation (ms) | 1.12.3 | 1.13.0 |
|---|---:|---:|
| add ×100 (one file each) | 112.2 | 112.9 (+0.6%) |
| add of 1,000 paths | 586.6 | 279.5 (−52.3%) |
| commit | 1.4 | 1.4 (−2.1%) |
| status, 200 files | 6.0 | 5.9 (−0.9%) |
| log --oneline, 300 commits | 26.4 | 26.8 (+1.5%) |
| checkout 100 changed files, there and back | 42.0 | 42.2 (+0.4%) |
| clone, 100 commits | 43.1 | 42.9 (−0.4%) |
| fsck, 100 commits | 36.9 | 36.7 (−0.6%) |

- **Nothing outside `add` moved beyond ±2.1%.**
- **The 1,000-path add halves its CPU.** The staging no longer deletes one row per path; patra's `DELETE` scans the table ([architecture 009](../architecture/009-patra-delete-scans-wal-syncs-per-page.md)).
- **The one-file add is unchanged.** A first cut read the whole index on every add and cost +24% here (113.1 → 140.3 ms); up to 24 paths it no longer reads it.

## `sit add` of 10,000 files, on disk

Wall-clock on ext4 (an SSD), `sync` before each run, one run each, load 10–11. Each file is a short line of text, 100 directories of 100.

| (ms) | 1.12.3 | 1.13.0 |
|---|---:|---:|
| new files | 64,861 | 7,804 (8.3×) |
| added again, unchanged | 69,826 | 933 (75×) |
| all modified | 92,118 | 15,251 (6.0×) |

`git add .` takes 583 ms for the new-file case. An earlier pair at load 16 gave 46,681 → 6,326 ms (new) and 44,927 → 574 ms (again).

Where 1.13.0's time goes, for the new-file case (6.3 s at load 17, from a build timing each phase):

| phase | ms |
|---|---:|
| walk and checks | 96 |
| blobs: read, hash, compress, insert, one batch | 2,523 |
| index: one transaction of 10,000 inserts | 3,653 |

- **Blobs.** 1.12.3 synced each insert, about 5 ms a file, which was nearly all of its time. 1.13.0 syncs once per 64 ([ADR 0018](../adr/0018-object-writes-in-batches.md)).
- **Index.** The transaction syncs its WAL once per page it touches, about 1,660 pages for 10,000 rows of 256-byte `STR` columns. That is patra's design, and an upstream ask.
- **Modified files** add the deletes: 417 statements of 24 paths, each scanning the table.

### patra in isolation

A scratch program against the 1.16.6 fold, to separate patra's costs from sit's. Over 4,000 rows already present, then one statement per row, in one transaction, on tmpfs:

| statement | 1,000 | 4,000 |
|---|---:|---:|
| `INSERT` | 20 ms | 88 ms |
| `INSERT`, after `DELETE … WHERE path = '…'` | 236 ms | 3,188 ms |
| `SELECT … WHERE path = '…'` | 26 ms | 108 ms |
| `DELETE … WHERE path = '…'` | 159 ms | 2,084 ms |
| `UPDATE … WHERE path = '…'` | 259 ms | 3,809 ms |

On ext4, 1,000 index rows in autocommit took 2,202 ms; in one transaction, 689 ms; 10,000 in one transaction, 6,767 ms. Clearing the table and reinserting 10,000 rows grew the file from 7.9 MB to 15.9 MB over ten rounds, which is why sit never rewrites the index wholesale.

## `log -- <path>`

Wall-clock, a 3,000-commit history made with `git fast-import` and packed by `git gc`, read in `.git/` mode. Twenty directories of five files, a file touched every commit, load 3–7.

| | ms |
|---|---:|
| `log --oneline` | 113 |
| `log --oneline -- .` | 113 |
| `log --oneline -- docs` (one level) | 134 |
| `log --oneline -- src/m3/f1.txt` (three levels) | 163 |
| `git log --first-parent --oneline -- src/m3/f1.txt` | 11 |

A first cut read each commit twice, once as the parent and again as the next step, and cost 257–267 ms for the same paths. The tree walk reads one tree per path component, so a path's cost grows with its depth, not with the tree's size. git's lead is its commit-graph and object caches (the 1.16.1 slot).

## Micro-benchmarks (`tests/sit.bcyr`)

No conclusion is drawn from them this time. The table is in the CSV.

- At load 10–12, alternating runs of the two builds' bench binaries, from one directory, moved rows by −34% … +67% in both directions, unchanged code included: `delta-tree-2000` +67%, `hex_prefix_valid` +67%, `tree_entry_name_valid` −35%.
- An earlier set, run from each build's own tree, moved −60% … +62%, with every pure-CPU row favouring one tree.
- The long rows agree within ±2%: ed25519 sign and verify, `is_ignored`, `patra-open-close`.
- 1.13.0 changes none of the functions the micro-benchmarks call.
