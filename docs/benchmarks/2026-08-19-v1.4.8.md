### The large tier is where 1.4.6 shows

The 100-commit default cannot see it. At `FIXTURE_COMMITS=1000`:

| | v1.4.4 | v1.4.5 | **v1.4.6+** |
|---|---:|---:|---:|
| `status-1000files` | 26.64× (137.74 ms) | 21.35× (110.15 ms) | **4.98× (22.46 ms)** |
| sit growth 100 → 1000 files | 24× | 21× | **5.2×** |

`.sit/index.patra` for that fixture went **277 MB → 672 KB** (422× smaller):
`sit add` had been rewriting the whole staging index per staged file, and
patra never reclaims deleted pages.

### ⚠ `clone`'s ratio is not a usable metric

Across four back-to-back runs at N=100, **sit held 71.4–71.9 ms (0.7% spread)
while git swung 9.96–14.47 ms (45%)** — moving the *ratio* 4.95× → 7.39× with
sit completely unchanged. Compare absolutes across snapshots, not ratios.

The 1.4.8 phase profile of `clone`:

| phase | N=100 | N=1000 | growth |
|---|---:|---:|---:|
| `walk_reachable_phased` | 35,512 µs | 1,823,692 µs | 51.4× |
| `copy_objects` | 21,952 µs | 484,133 µs | 22.1× |
| `materialize_target` | 9,225 µs | 91,260 µs | 9.9× |

And the fixture is **not 10× bigger — it is 22×**: it adds one new file per
commit, so tree sizes grow linearly and total tree bytes are quadratic in commit
count (300 → 3,000 objects, but 1,332 KB → 29,272 KB of store). Measured against
bytes rather than commits, `clone` is 1.5× worse than linear and the walk 2.3×.
git moves the same content in 2.4× the time because it delta-compresses trees —
that gap is the packing item, not an algorithmic defect.

## Micro-benchmarks

v1.4.8 HFS-ignorable check replaced an O(1) length-mismatch reject with a full
UTF-8 decode, costing **79 → 129 ns (+63%)** on a path `parse_tree` runs per
entry. A first-significant-codepoint pre-filter brought it back to **89 ns**
(the untouched `refname_valid-good` drifted 260 → 296 ns on this host, so 89 ns
